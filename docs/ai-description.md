# MindWP / Mindwp-Design — Project Brief You are working inside the existing repo **`mindwp/Mindwp-Design`**, a Vite design sandbox used to create and refine MindWP page designs before they are later recreated or migrated into the main production website. You have live access to this repo. **Read the actual files** for current structure, routing, page references, theme, and patterns — do not rely on a static file list. This brief gives you the rules and intent; the repo gives you the ground truth. ## Sandbox priorities Strong UI design, clear business meaning, practical page structure, page-owned JSX, premium visual quality, and easy future migration into the main MindWP website. - Do not work in the main Mindwp folder unless explicitly asked. - Do not port anything unless explicitly asked. - Do not create a new project unless explicitly asked. ## Structure rules Follow the existing sandbox structure (read `src/app/App.tsx`, `src/app/Home.tsx`, and `src/app/pages/` to learn the current pattern). Prefer direct page JSX while proving page quality. - Do not over-abstract. - Do not create data files unless the task clearly requires them. - Do not create shared components just to make code look cleaner. - Do not refactor unrelated files unless necessary for the requested page to work. - If a file referenced in a task is missing, ignore it and use the nearest equivalent in the repo. ## MindWP positioning MindWP builds conversion-focused website systems with connected handling for established service businesses and specialist clinics. The website is the public control point. For specialist clinics, the website is also the practice front door. MindWP helps a business or practice make the service/treatment/offer clear, build trust before contact, capture enquiries (calls, forms, bookings, quote requests, consultation requests), and connect those moments to response, routing, follow-up, ownership, reviews, proof, and ongoing improvement. MindWP is not just "website design." It is the website **and** the business/practice handling around it. ### Must not sound like A generic web design agency, cheap WordPress package provider, random digital service catalog, SaaS product, AI chatbot vendor, AI automation bro offer, CRM/tool reseller, backend platform reseller, SEO ranking-hype provider, generic doctor marketing agency, healthcare software company, EMR implementation provider, compliance consultant, portfolio-only design shop, or a feature dump. ### Should feel like Practical, operational, calm, premium, conversion-focused, system-first, commercially serious, service-business aware, clinic/practice aware, and grounded in real business and patient-decision friction. Public copy starts from working-day realities — calls, local searches, forms, messages, quotes, bookings, consultation requests, treatment enquiries, jobs, appointments, reviews, inboxes, staff pressure, missed replies, follow-up gaps, local trust, patient trust, proof. **Start with the buyer's day before naming the system.** ## The five public systems There are exactly five, and never a sixth: 1. Smart Website Systems 2. Local SEO Authority Systems 3. Lead Response & Handling Systems 4. Follow-Up & CRM Systems 5. Reputation & Review Systems No `/systems` route. No `/portfolio` route. No public topic hubs. **Revenue Recovery** is an internal/cross-system improvement lens only. It must never become a public offer, system, service page, route, CTA, nav pillar, card, form, panel, category, or related-content cluster. > Note on naming: the file `AILeadHandling.tsx` may exist in the repo, but public language must always say **"Lead Response & Handling," never "AI Lead Handling."** Treat the filename as legacy; the mismatch is fine to leave unless a task asks to rename it. ## Implementation services These sit **under** Smart Website Systems and are build paths, not primary systems: WordPress Development, Elementor, Bricks Builder, Divi 5, WooCommerce, Website Redesign / System Rebuild. Explain implementation choice through clarity, trust, enquiry capture, maintainability, performance, responsive behavior, editable structure, and connected handling. They must not become builder fan pages, cheap freelancer pages, generic WordPress pages, pixel-perfect commodity pages, or tool feature explainers. Tool-aware buyers may search for Elementor, Bricks, Divi, WordPress, WooCommerce, or redesign — capture that intent and move the buyer toward a smarter website system. The tool is the route, not the main value. ## Audience lanes Two lanes, expanding over time. **Home Services** (active: HVAC, plumbing, roofing, foundation repair, septic services, tree service). Focus on calls, quote requests, bookings, local trust, service-area clarity, missed response, quote follow-up, reviews, proof, owner visibility. Must not drift into generic contractor marketing, ranking hype, or cheap lead-gen language. **Healthcare Practices** (active: dental implant, orthodontic, oral surgery, dermatology, ENT/sinus, podiatry, hearing aid/audiology, physiotherapy, optometry, orthopedic clinics). These behave like practice-front-door landing pages — focus on patient trust, service/treatment clarity, consultation requests, booking confidence, practice communication, pre-visit context, response, follow-up, reviews, proof. Must not drift into healthcare software, EMR implementation, compliance claims, hospital operations, generic doctor marketing, treatment-outcome claims, or patient-result claims. ## Design direction Use the current Mindwp-Design pages as the quality standard for visual quality, spacing, tone, and sandbox patterns (read `src/styles/theme.css`, the Header/Footer components, and the Tier 1 pages). Do not blindly clone their layouts. Preferred: dark hero sections, calm white/mist rhythm, premium spacing, strong editorial sections, connected-handling surfaces, website-as-control-point maps, practice-front-door maps, find → verify → trust → contact paths, enquiry-to-handling paths, consultation-to-follow-up paths, operating maps, signal boards, before/after panels, proof stacks, scenario-led sections, diagnostic CTA panels, fit filters. Avoid: generic card grids everywhere, repeated board/card/table sections, generic dashboards, fake SaaS UI, tech-card filler, process steps everywhere, AI robot visuals, SEO ranking dashboards, generic doctor imagery, stock handshake photos, decorative icon grids, fake screenshots, fake testimonials, fake metrics, fake phone numbers, fake ratings/review counts. Each page needs a clear page argument and distinct section silhouettes. Don't make every section a board, card grid, timeline, or dashboard — use editorial and scenario-led layouts where they fit better. ## Motion Use existing motion/reveal classes only if useful: `mw-animate-section`, `mw-animate-list`, `mw-animate-stagger`, `mw-animate-fade`, `mw-animate-up`, `mw-animate-panel`, `mw-animate-line`. Do not add animation libraries. Motion is calm and purposeful — no scroll-jacking, parallax, cursor effects, fake dashboard animation, loops, or loading delays. No section should depend on animation to be understood. ## Page workflow For a **new page build**, follow the full sequence: BUSINESS REALITY → BUYER RECOGNITION → PAGE INTENT → PATTERN → SECTION DESIGN → JSX → IMPROVE/REWRITE CONTENT → REVIEW → SYSTEMIZATION For **edits to an existing page**, you can skip ahead to SECTION DESIGN. Before implementation: understand the business/practice moment, define the page argument, define each section's job, decide which sections are editorial/visual/mockup/scenario/fit/CTA, avoid repeated silhouettes, and protect the five-system hierarchy. Start industry pages from real working moments (not service-page templates), implementation pages from build-path buyer intent (not tool features), and Tier 1 service pages from the system problem and buyer recognition (not service mechanics). ## Copy guardrails Use public buyer-facing language: calls, forms, messages, quotes, bookings, consultation requests, local trust, service area, reviews, proof, owner, status, next step, handoff, response path, review path. Avoid leading with: platform, backend, infrastructure, automation engine, workflow, trigger, pipeline, opportunity, lifecycle, dashboard, integration, GoHighLevel, HighLevel, GHL. Use tool names only on explicit implementation pages, and even then the tool is the route, not the value. ## CTA posture Use diagnostic CTAs: *Request a Website Review · Review my website system · Review my local visibility · Review my response path · Review my follow-up path · Review my reputation path · Review my home-service website and handling path · Review my plumbing website and enquiry path.* Avoid: Start a Conversation · Book a demo · Get guaranteed results · Dominate Google · Get more revenue · Try our platform. No ranking, revenue, conversion, response-time, or review-volume guarantees. ## Safety / fake-proof rules Never use fake phone numbers, ratings, review counts, testimonials, client names, exact timestamps, statistics, screenshots, unsupported case-study claims, medical-outcome claims, treatment-result claims, healthcare compliance claims, same-day/within-minutes promises, or guaranteed ranking/performance claims. Use illustrative labels instead: Recent verified reviews · Local area covered · Quote path visible · Direct line · Response path active · Common problems answered · Owner attached · Next step visible · Review theme · Proof placed near the decision. ## Validation Use **pnpm only**. Run `pnpm build` after edits (or the specific command the task provides). If the environment has no install/build access, report the intended changes and note that build was not attempted. Check for banned language: GoHighLevel, HighLevel, GHL, Voice AI, Conversation AI, chatbot, Revenue Growth, Revenue Recovery, Start a Conversation, and any fake ratings/phone numbers/testimonials/client names, guaranteed rankings, or same-day/within-minutes promises. ## How to work **If the task says planning only:** do not edit files or write code. Produce a clear plan and wait for approval. **If the task says implement:** edit only the specified files, don't touch unrelated pages, keep the current sandbox pattern, run build after edits, and report files changed, sections changed, sections protected, and build result. Do not ask questions during execution unless there's a build-breaking issue or a real strategic contradiction.
