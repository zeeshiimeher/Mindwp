## Purpose

The page rebuild should be docs-led, not renderer-led.

These briefs explain what each important page must help the buyer understand. They do not define final section order. They do not require exact sections. They do not ask Claude to copy existing pages.

The rebuild process remains:

```text
BUSINESS REALITY -> BUYER RECOGNITION -> PAGE INTENT -> PATTERN -> SECTION DESIGN -> JSX -> APPROVAL -> SYSTEMIZATION
```

Existing files may be reviewed for buyer problems, useful ideas, and implementation constraints. They must not dictate final section order, renderer structure, page data shape, component choice, visual pattern, or final copy.

## Global Rebuild Rules

Every rebuilt page should support the current positioning:

> MindWP builds conversion-focused website systems with connected handling for established service businesses.

Meaning:

- Website systems make the offer clear, build trust, guide visitors, capture enquiries, and create a visible public control point.
- Connected handling is the response, routing, follow-up, ownership, CRM visibility, review request, proof capture, and recovery path around the website.
- The page should make the buyer recognise where work slips away before explaining system structure.

Do not let pages become:

- generic agency service pages
- SaaS landing pages
- AI chatbot pages
- CRM platform setup pages
- cheap website package pages
- SEO ranking-hype pages
- builder/platform fan pages
- generic feature grids
- process steps everywhere
- dashboards without business meaning

Use custom page-owned JSX when the page needs a specific leak map, connected-handling surface, signal board, operating map, fit filter, proof stack, or scenario board.

Extract shared components, data shapes, metadata, graph rules, and stricter CTA rules only after the page is approved.

## Page Brief Format

Each page brief uses:

- **Type** — page kind and funnel role.
- **Owning system** — the active system that owns the page.
- **Strategic job** — what the page must help the buyer understand.
- **Buyer recognition** — the situation the buyer should see themselves in.
- **Must make visible** — business realities the page should show.
- **Must not become** — drift risks.
- **Useful patterns** — possible communication/design patterns, not mandatory sections.
- **CTA posture** — the kind of next step that fits.
- **Proof/trust needs** — evidence or trust support the page may need.
- **Rebuild note** — special direction for Claude/Codex.

# Core Public Pages

## Homepage

**Type:** Primary entry page / whole-system recognition page  
**Owning system:** Whole MindWP model, with Smart Website Systems as the public anchor  
**Primary role:** Create recognition, explain the connected path, and route visitors into the right next step.

### Strategic Job

Help established service-business owners recognise that their business already has activity, but work is slipping between moments.

The homepage should make this plain:

- customers search
- they check trust
- they visit service pages
- they call, message, book, or submit forms
- enquiries land somewhere
- response may be slow or scattered
- follow-up may depend on memory
- completed work may not become reviews or proof

The homepage should then explain that MindWP builds conversion-focused website systems with connected handling around those weak points.

### Buyer Recognition

The buyer should feel:

> We are not starting from zero. We already get calls, visits, jobs, customers, and reviews. But too much slips away because the website, response, follow-up, and proof path are not connected clearly enough.

### Must Make Visible

- work slipping between search, trust, contact, response, follow-up, reviews, and proof
- the website as the visible control point
- connected handling around enquiries, response, follow-up, reviews, and proof
- the five active systems without turning the homepage into a service catalog
- why the problem is connected, not a pile of separate digital services
- fit for established service businesses

### Must Not Become

- a generic agency homepage
- a web design portfolio homepage
- a SaaS product homepage
- a six-card service menu
- an automation or AI homepage
- a process diagram page
- a blog/resource hub

### Useful Patterns

Possible patterns, not required sections:

- Work Comes In / Too Much Slips Away recognition surface
- find -> trust -> contact -> handled -> proof operating path
- leak map across the buyer journey
- website-as-control-point visual
- connected-handling surface around calls/forms/messages/follow-up/reviews
- active systems as connected moments, not equal random services
- fit filter
- proof/scenario board
- diagnostic CTA panel

### CTA Posture

Homepage CTA should diagnose the whole website and handling path.

Good directions:

- Check my website system
- Review my website and handling path
- Find where work is slipping
- Request a system review

Avoid pushing a narrow service too early.

### Proof / Trust Needs

The homepage should eventually support:

- scenario examples
- before/after operating maps
- case studies or system examples
- proof that MindWP understands service-business operations
- practical founder capability without turning the page into a resume

### Rebuild Note

Do not copy existing homepage section order. Rebuild from recognition first. The homepage should feel like a calm, premium operating diagnosis, not an agency pitch.

- call/form/message handling

- what happens next

The contact page should reduce ambiguity. It should not ask technical questions too early.

# Implementation Service Pages

## Implementation Services Group

**Type:** Implementation pathway pages under Smart Website Systems  
**Owning system:** Smart Website Systems  
**Primary role:** Explain practical build paths without turning MindWP into a generic builder agency.

### Strategic Job

Implementation pages should help buyers who search by platform or build need understand how that implementation path supports a conversion-focused website system.

They should answer:

- why this path may fit a service business
- what business problem the website must solve
- how clarity, trust, enquiry capture, and connected handling improve
- what the platform/builder is useful for
- how the page connects back to Smart Website Systems

### Applies To

- WordPress Development
- Elementor
- Bricks Builder
- Divi 5
- WooCommerce
- Website Redesign / System Rebuild

### Buyer Recognition

The buyer may think they need a platform or rebuild. The page should help them understand that the tool matters only because the website must be clear, fast, editable, trustworthy, and connected to handling.

### Must Make Visible

- website-system parent relationship
- practical implementation fit
- maintainability and editing where relevant
- performance where relevant
- ecommerce fit where relevant
- rebuild as structure improvement, not only visual refresh
- connected handling around the website

### Must Not Become

- generic WordPress agency page
- Elementor/Bricks/Divi fan page
- affiliate-style comparison
- cheap package page
- page-count pricing page
- plugin stack page
- equal strategic pillar

### Useful Patterns

- implementation pathway panel
- tool choice vs business fit contrast
- rebuild weak structure vs connected website system
- maintainability map
- platform fit filter
- website clarity before builder choice
- Smart Website Systems parent link

### CTA Posture

Good directions:

- Check my website system
- Talk through the right implementation path
- Review my website rebuild path

### Rebuild Note

Implementation pages should inherit Smart Website Systems tone. They may discuss technology, but only after the business reason is clear.

# Rebuild Readiness Checklist

Before rebuilding a page, confirm:

- the page type is clear
- the owning active system is clear where relevant
- the buyer recognition moment is clear
- the page intent is clear
- the page does not copy existing renderer order
- the page does not start with internal taxonomy before recognition
- the page has a likely pattern direction
- CTA posture is diagnostic
- proof is real, clearly illustrative, or absent
- implementation pages resolve upward to Smart Website Systems
- Revenue Recovery remains a layer only
- design can use page-owned JSX where needed

If any item is unclear, clarify the page brief before writing or coding.
