# Case Study System — Execution Plan (MindWP)

This document defines the FULL planning, decision, and execution strategy for case studies.

This is NOT content.
This is NOT marketing.

This is:
→ system-level planning
→ execution control
→ rewrite strategy

--------------------------------------------------
🧠 GOAL
--------------------------------------------------

Build case studies that:

- feel real (not AI, not fake)
- feel slightly imperfect
- are believable to a human reader
- support trust (not oversell)
- fit system positioning (NOT web design)

--------------------------------------------------
⚠️ CORE PRINCIPLE
--------------------------------------------------

Case studies are NOT:

- reports
- dashboards
- sales pages
- feature explanations

Case studies ARE:

→ observed business situations where something changed

--------------------------------------------------
🚨 CURRENT SYSTEM PROBLEM
--------------------------------------------------

Current issues identified:

1. Over-precise metrics
   → looks fake / generated

2. Perfect transformation arcs
   → unrealistic

3. Repeated structure
   → template feel

4. System-heavy language
   → breaks immersion

5. Mid-CTA injection
   → breaks trust

--------------------------------------------------
✅ STRATEGY DECISION (LOCKED)
--------------------------------------------------

We will NOT:

❌ full rebuild of system
❌ light copy tweaks

We WILL:

✅ Controlled realism rewrite

--------------------------------------------------
🧩 SYSTEM ADJUSTMENTS (NO BREAKING CHANGES)
--------------------------------------------------

Keep:

- template structure
- validators
- registry system

Change:

- data usage style
- language
- narrative flow
- metrics realism

--------------------------------------------------
🧠 CASE STUDY MODEL (NEW)
--------------------------------------------------

Each case study must follow:

1. Situation
2. What was going wrong
3. What changed
4. What improved (not perfect)

NOT:

❌ problem → solution → result (clean model)

--------------------------------------------------
🧱 TEMPLATE USAGE RULE
--------------------------------------------------

Use 4–6 sections maximum.

Rules:

- do not use the full template by default
- do not force a fixed section order
- choose only the sections that make the case readable and believable
- if a section adds polish instead of proof, remove it

--------------------------------------------------
📊 METRICS RULE (CRITICAL)
--------------------------------------------------

❌ DO NOT:

- use exact numbers everywhere
- stack multiple perfect metrics
- show dashboard-level precision

✅ USE:

- ranges
- approximations
- partial improvements
- observable changes when numbers are weak

Examples:

❌ +£3,842/month
✅ around £3k–£4k recovered

❌ 93% conversion
✅ noticeably more enquiries converting

--------------------------------------------------
🧠 REALISM LAYER (MANDATORY)
--------------------------------------------------

Each case study MUST include at least one of:

- delay
- inconsistency
- human limitation

Optional realism layers:

- missed follow-up
- partial adoption
- uneven results

Example:

"Not every lead responded. But enough did to make a difference."

--------------------------------------------------
🧩 LANGUAGE RULES
--------------------------------------------------

❌ REMOVE:

- system
- solution implemented
- conversion rate improved
- workflow optimization
- implementation language that reads like a report

✅ USE:

- natural phrasing
- real situations
- imperfect tone

Examples:

❌ "The system improved follow-up"
✅ "Quotes stopped sitting there untouched"

--------------------------------------------------
🧱 STRUCTURE RULE
--------------------------------------------------

- NOT all sections must be used
- order can vary
- avoid predictable flow

BUT:

- must remain readable
- must not confuse user

--------------------------------------------------
🔁 CASE STUDY TYPES (FOR VARIATION)
--------------------------------------------------

Each case study should belong to ONE dominant type:

1. Missed lead recovery
2. Slow follow-up improvement
3. Quote conversion improvement
4. Visibility / enquiry increase
5. Operational clarity

Each type must feel different.

### 1. Missed Lead Recovery

Focus:

- missed calls
- unanswered enquiries
- first-response failure

Allowed sections:

- situation
- what was going wrong
- what changed
- result
- soft CTA

### 2. Follow-Up Improvement

Focus:

- proposals left untouched
- reminders never sent
- delayed replies after first contact

Allowed sections:

- situation
- friction
- change
- partial outcome
- soft CTA

### 3. Quote Conversion Improvement

Focus:

- estimates going quiet
- longer decision windows
- stalled mid-funnel conversations

Allowed sections:

- situation
- what was going wrong
- comparison moment
- what changed
- result
- soft CTA

### 4. Visibility / Enquiry Increase

Focus:

- better-fit local enquiries
- clearer service discovery
- more relevant inbound volume

Allowed sections:

- context
- before
- what changed
- observed improvement
- soft CTA

### 5. Operations

Focus:

- handoff clarity
- fewer missed details
- steadier day-to-day handling

Allowed sections:

- context
- operational problem
- change
- what improved
- soft CTA

--------------------------------------------------
🏷 NAMING SYSTEM (UPDATE)
--------------------------------------------------

❌ OLD:

hvac-emergency-lead-routing

✅ NEW:

hvac-winter-call-overflow
roofing-quotes-not-followed-up

→ Situation-first naming

Rules:

- slug = situation-first
- title = real moment
- SEO title = clearer version of the same moment

--------------------------------------------------
📣 CTA RULE
--------------------------------------------------

- NO aggressive CTA
- NO mid-flow push
- ONLY soft CTA at end

--------------------------------------------------
🧠 VALIDATION CHECK
--------------------------------------------------

Before finalizing each case study:

1. Does this feel too perfect?
2. Does this feel templated?
3. Does this sound like marketing?
4. Could this happen in real life?

If any FAIL → rewrite

--------------------------------------------------
⚙️ EXECUTION PLAN
--------------------------------------------------

1. classify type
2. rename
3. choose sections
4. rewrite
5. validate realism

### EXECUTION FLOW DETAIL

#### 1. Classify Type

- choose one dominant case study type
- confirm the main business moment being proven

#### 2. Rename

- rewrite slug around the situation
- rewrite title around the observed moment
- rewrite SEO title into a clearer search-safe version

#### 3. Choose Sections

- select 4–6 sections only
- remove any section that reads like template filler
- keep order flexible if the narrative reads better another way

#### 4. Rewrite

- rebuild the case around observed reality
- keep language natural and non-report-like
- keep metrics approximate unless the precision is genuinely defensible

#### 5. Validate Realism

- confirm at least one realism layer is visible
- confirm the narrative does not read too cleanly
- confirm the CTA stays soft and end-only

--------------------------------------------------
🏁 END STATE
--------------------------------------------------

Case studies should feel:

- believable
- slightly imperfect
- real-world grounded
- not selling
- not templated

→ This builds trust instead of suspicion
