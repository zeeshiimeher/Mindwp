# Case Study System — Execution Plan (MindWP)

This document defines the FULL planning, decision, and execution strategy for case studies.

This is NOT content.
This is NOT marketing.

This is:
→ system-level planning
→ execution control
→ rewrite strategy

--------------------------------------------------
🧠 GOAL
--------------------------------------------------

Build case studies that:

- feel real (not AI, not fake)
- feel slightly imperfect
- are believable to a human reader
- support trust (not oversell)
- fit system positioning (NOT web design)

--------------------------------------------------
⚠️ CORE PRINCIPLE
--------------------------------------------------

Case studies are NOT:

- reports
- dashboards
- sales pages
- feature explanations

Case studies ARE:

→ observed business situations where something changed

--------------------------------------------------
🚨 CURRENT SYSTEM PROBLEM
--------------------------------------------------

Current issues identified:

1. Over-precise metrics
   → looks fake / generated

2. Perfect transformation arcs
   → unrealistic

3. Repeated structure
   → template feel

4. System-heavy language
   → breaks immersion

5. Mid-CTA injection
   → breaks trust

--------------------------------------------------
✅ STRATEGY DECISION (LOCKED)
--------------------------------------------------

We will NOT:

❌ full rebuild of system
❌ light copy tweaks

We WILL:

✅ Controlled realism rewrite

--------------------------------------------------
🧩 SYSTEM ADJUSTMENTS (NO BREAKING CHANGES)
--------------------------------------------------

Keep:

- template structure
- validators
- registry system

Change:

- data usage style
- language
- narrative flow
- metrics realism

--------------------------------------------------
🧠 CASE STUDY MODEL (NEW)
--------------------------------------------------

Each case study must follow:

1. Situation
2. What was going wrong
3. What changed
4. What improved (not perfect)

NOT:

❌ problem → solution → result (clean model)

--------------------------------------------------
📊 METRICS RULE (CRITICAL)
--------------------------------------------------

❌ DO NOT:

- use exact numbers everywhere
- stack multiple perfect metrics
- show dashboard-level precision

✅ USE:

- ranges
- approximations
- partial improvements

Examples:

❌ +£3,842/month
✅ around £3k–£4k recovered

❌ 93% conversion
✅ noticeably more enquiries converting

--------------------------------------------------
🧠 REALISM LAYER (MANDATORY)
--------------------------------------------------

Each case study MUST include at least 2:

- delay
- missed follow-up
- inconsistent results
- human behavior
- partial adoption

Example:

"Not every lead responded. But enough did to make a difference."

--------------------------------------------------
🧩 LANGUAGE RULES
--------------------------------------------------

❌ REMOVE:

- system
- solution implemented
- conversion rate improved
- workflow optimization

✅ USE:

- natural phrasing
- real situations
- imperfect tone

Examples:

❌ "The system improved follow-up"
✅ "Quotes stopped sitting there untouched"

--------------------------------------------------
🧱 STRUCTURE RULE
--------------------------------------------------

- NOT all sections must be used
- order can vary
- avoid predictable flow

BUT:

- must remain readable
- must not confuse user

--------------------------------------------------
🔁 CASE STUDY TYPES (FOR VARIATION)
--------------------------------------------------

Each case study should belong to ONE dominant type:

1. Missed lead recovery
2. Slow follow-up improvement
3. Quote conversion improvement
4. Visibility / enquiry increase
5. Operational clarity

Each type must feel different.

--------------------------------------------------
🏷 NAMING SYSTEM (UPDATE)
--------------------------------------------------

❌ OLD:

hvac-emergency-lead-routing

✅ NEW:

hvac-winter-call-overflow
roofing-quotes-not-followed-up

→ Situation-first naming

--------------------------------------------------
📣 CTA RULE
--------------------------------------------------

- NO aggressive CTA
- NO mid-flow push
- ONLY soft CTA at end

--------------------------------------------------
🧠 VALIDATION CHECK
--------------------------------------------------

Before finalizing each case study:

1. Does this feel too perfect?
2. Does this feel templated?
3. Does this sound like marketing?
4. Could this happen in real life?

If any FAIL → rewrite

--------------------------------------------------
⚙️ EXECUTION PLAN
--------------------------------------------------

STEP 1:
Lock system rules (this doc)

STEP 2:
Rename case studies (situation-based)

STEP 3:
Rewrite data (NOT template)

STEP 4:
Inject realism layer

STEP 5:
Reduce metric precision

STEP 6:
Final validation

--------------------------------------------------
🏁 END STATE
--------------------------------------------------

Case studies should feel:

- believable
- slightly imperfect
- real-world grounded
- not selling
- not templated

→ This builds trust instead of suspicion
