## Service Page Copywriting Tone (Locked)

Service pages must communicate system concepts in clear business language.

The audience is service-business owners, not technical consultants.

Tone requirements:

- Calm and consultative
- Clear and direct
- Operational rather than promotional
- Written in simple, natural English

Service pages must avoid:

- marketing hype or exaggerated claims
- consultant-style jargon
- overly technical explanations
- robotic or repetitive phrasing

Examples of wording that must not be overused:

- structure
- structural alignment
- infrastructure layer
- operational alignment
- framework architecture

When these concepts are required, they must be explained using natural business language instead.

Preferred style: Explain the outcome rather than the abstract concept.

Sentence style rules:

- Prefer shorter sentences
- Avoid corporate buzzwords
- Avoid sounding like agency marketing copy
- Avoid overly polished AI-style writing

## Unified Content Hierarchy (Canonical Definition)

All content follows this hierarchy. This is the single content model used across all MindWP documentation.

Blog
→ Resource
→ Industry
→ Case Study
→ Feature
→ Service

- Blog captures discovery queries, problems, and discussions.
- Resource explains operational frameworks and repeatable systems.
- Industry applies those systems in a specific service-business vertical.
- Case Study provides proof of implementation.
- Feature explains a system capability within the broader framework.
- Service represents the infrastructure layer itself.

Each layer reinforces the layer beneath it. No layer should exist in isolation.

Authority flow:

Blogs strengthen Resources.
Resources strengthen Industry pages.
Industry pages strengthen Case Studies.
Case Studies strengthen Feature pages.
Feature pages strengthen Services.

This flow preserves the systems-first positioning model and prevents discovery content from replacing system explanations.

---

## Content Type Definitions & Roles

Each content type has one clear job. No cross-type blending is permitted.

### Blog

- Purpose: visibility engine and authority-building layer
- Function: problem-based education, system explanation, decision clarification
- Allowed forms: problem-based articles, system explainer articles, comparison articles
- Not allowed: trend-based content without system framing, tool-roundup spam, step-by-step implementation guides (those belong in Resource layer)
- SEO intent: problem keywords, mid-intent CRM queries, structural explanation queries
- Tone: calm, structured, clear, no hype

### Resource

- Purpose: structured knowledge asset and reference-level depth layer
- Function: framework-driven, evergreen, repeatable system guidance
- Allowed categories: frameworks, checklists, blueprints, audit guides
- Not allowed: opinion-first content, sales-heavy framing, trend commentary, news discussion
- SEO intent: checklist, template, guide, framework, blueprint, audit intent
- Access model: open access unless a separate business rule changes it

### Case Study

- Purpose: implementation narrative and trust layer
- Function: demonstrate real-world application of Smart Website Systems
- Structural model: industry-led and system-structured
- Not allowed: hype narratives, fabricated proof, dramatic storytelling
- SEO intent: may target implementation-example intent when it does not collide with industry commercial keywords

### Industry Page

- Purpose: commercial positioning
- Function: vertical-specific relevance, offer-focused intent
- Shows: Related Services + Related Case Studies + Related Resources

### Feature Page

- Purpose: system capability hub
- Function: explain what a system can do, where it applies, how it connects to implementation layers
- Must not read like generic feature lists
- Must explain operational capability inside the wider system architecture

### Service Page

- Purpose: implementation-focused system explanation
- Shows: Related Services ONLY (max 3)
- Must remain clean, focused, and minimal

### Decision Logic

- If content answers why, how, or what is wrong → blog content
- If content defines a repeatable system → resource
- If content tells a structured scenario → case study
- If content sells vertical relevance → industry page

## Content Creation Order Rule (Locked)

When creating new content items, relationships must always be determined in the following order:

This order prevents incorrect graph relationships and ensures content is mapped to the correct system before being applied to a specific industry.

## Content Flow and Relationship Model (Locked)

Blog → Resource → Industry → Case Study → Feature → Service

- Blog pages introduce the problem and early learning.
- Resource pages explain the framework behind the problem.
- Industry pages make that framework practical for a specific business type.
- Case studies prove real implementation.
- Feature pages explain system capabilities.

Each page type has one clear job:

- Blog: learning and problem discovery.
- Resource: system understanding and framework depth.
- Feature: capability explanation.
- Industry: real-world application in a specific vertical.
- Case Study: proof that the system works in real operations.
- Service: implementation path and delivery scope.

- 1-2 core resources that explain the system approach for that industry

- selected case study references that match the industry's problems

Industry pages should connect learning to evidence, then to implementation.

### Related Content Rules (Above and Below CTA)

Above CTA: show the next logical educational step, keep links close to the current topic and system.
Below CTA: show proof and implementation paths, prioritize relevant case studies and service destinations.

Practical rule: Above CTA = understanding. Below CTA = decision support.

- The UI layer is strict and controlled. It shows only the highest-relevance items, capped at 3.

Content relationships flow upward through the hierarchy. Lower-hierarchy content links toward higher-hierarchy content — not the other way around.

3. Service pages must never display blog posts, resources, case studies, industries, or features.
4. Blog posts must never appear on service pages, case study pages, or feature pages.
5. No new related content section may be added to any page type without updating this master definition.
6. Any content relationship not explicitly permitted here is prohibited.

## AUTHORITY RESOLUTION SYSTEM (LOCKED)

The authority resolver converts graph relationships into ranked related content for each page.

### Ranking Factors

Relationships are ranked based on two factors, in order of priority:

1. **Metadata overlap** — the degree to which two content nodes share systems, topics, and industries. Higher overlap produces higher ranking.
2. **Relationship type priority** — ranked: relatesTo (highest, priority 300), supports (200), validates (100). Reverse edges score lower (90, 80, 70).

### Resolution Principle

Relevance drives ranking. High metadata overlap produces high ranking. No metadata overlap produces low ranking. The system is deterministic and precomputed at build time.

## 🔒 UI Architecture (LOCKED)

UI components never compute relationships, filter graph data, calculate authority, or access the raw graph directly.

All data flows through the Query API (`src/lib/graph/query.ts`):
- `getRelatedContent()` — related content slots
- `getTopicCluster()` — topic-based clusters
- `getSystemCluster()` — system-based clusters
- `getContentByIndustry()` — industry-based clusters

UI components (`src/components/system/`) consume the Query API and render data using configuration from `src/config/ui-intelligence.ts`.

System components:
- SmartRelatedSection — renders related content per slot, driven by RELATED_SECTION_LABELS config
- JourneyNavigator — renders next-step navigation, driven by JOURNEY_CONFIG
- SmartCTA — renders page-type-aware CTA, driven by CTA_CONFIG (intensity: soft/mid/strong)
- GraphAwareSidebar — renders sidebar with related items + journey card
- ClusterPageLayout — renders topic/system/industry cluster pages

No UI component contains hardcoded slugs, scores, or relationship logic.

## 🔒 Intelligence Engine (LOCKED)

The intelligence engine is a deterministic, precomputed authority scoring system.

Components:
- `computeAuthorityScores()` — computes authority score per node based on edge weights + context boosts
- `resolveSlot()` — resolves top 3 related items per slot using edge priority scoring
- Static authority map — precomputed at build time, regenerated when content changes

The engine does NOT use AI, NLP, embeddings, or runtime computation.

JSON output structure (authority map per node):
- `services[]`, `resources[]`, `blog[]`, `caseStudies[]`, `industries[]` — each containing `{ title, slug, path, nodeType }`

No changes to this system without explicit architectural review.

## Content Volume Balance Rule

Content volume must follow the priority lane model. Primary Lane content must always exceed Expansion Lane content. Expansion Lane must exceed Coverage Lane.

- Do not allow equal volume across all industry lanes.

## SEO Collision Prevention Rule

No two content items may target the same primary keyword or the same topic + industry combination.

- Resources must not compete with industry commercial keywords.
- Resources must not compete with blog problem keywords.
- Blogs must not absorb framework or checklist keyword space.
- Each topic + industry combination may exist only once across blog content.

Cross-reference: Keyword Collision Rules, Unique Topic Cluster Rule (this document).

## Content Role Drift Rule

Each content type must stay within its assigned role. If a content piece begins behaving like another content type, it must be corrected.

- A blog must not become a resource (step-by-step frameworks belong in resources).
- A resource must not become a blog (opinion/trend commentary belongs in blog).
- A case study must not become a marketing page (proof, not promotion).
- A service page must not become a content hub (no blog/resource/case study display).

Cross-reference: Content System Integrity Rule, Content Type Definitions & Roles (this document).

## Graph Consistency Rule

All content nodes must declare valid metadata that matches the canonical identifier registries. Invalid or orphaned metadata breaks graph relationships.

- systems[] must use canonical system identifiers.
- industries[] must use canonical industry identifiers.
- topics[] must use canonical topic identifiers.
- New identifiers must be added to the canonical registry before use.
- Content without required metadata fields must fail validation.

## AI Content Generation Limit Rule

AI-generated content must follow the content creation order (Topic → System → Industry) and must not duplicate existing metadata combinations.

- AI must not propose titles before defining topic, system, and industry metadata.
- If a proposed article duplicates an existing systems[] + topics[] + industries[] combination, it must be rejected.
- AI must not generate content outside the approved content hierarchy or outside the approved archetypes.

## Resource Duplication Prevention Rule

No two resources may explain the same system framework. Global resources explain a system once. Industry resources demonstrate application but must not re-teach the full framework.

- Before creating a new resource, confirm no existing resource covers the same system + topic combination.
- Industry context resources must reference the global system resource, not duplicate it.

Cross-reference: Resource Architecture Model, System Explanation Layer Rule (this document).

## Blog Scope Limitation Rule

Blog posts must remain within their editorial scope. Blogs are discovery and problem-exploration content, not framework guides or implementation documentation.

- Blog posts must not contain step-by-step implementation frameworks (those belong in resources).
- Blog posts must not contain FAQ sections unless the topic explicitly warrants clarification.
- Blog posts must link upward to resources and industry pages, never downward into service pages.

Cross-reference: Blog Writing Standard (this document).

## Content Maintenance Rule

Published content must be reviewed and updated when upstream architecture changes. Stale content that contradicts current architecture must be corrected or removed.

- When a service page is renamed or restructured, all content linking to it must be updated.
- When industry priority lanes change, content volume and link emphasis must be rebalanced.
- When metadata registries are updated, existing content using old identifiers must be migrated.

## Title Uniqueness Rule

No two content items across the entire site may have the same title or SEO title. Duplicate titles create SEO cannibalization and confuse the content graph.

- Every title must be unique across blog, resource, case study, feature, industry, and service pages.
- SEO titles must be unique across the full site.
- Before creating a new content item, verify the proposed title does not duplicate an existing one.
